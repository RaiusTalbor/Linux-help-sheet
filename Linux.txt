Remote Control (SSH, transfering files)
------------------------------------------------------------------------------------------------------------------------------

Connection - The Basics
-------------------

ssh <user>@<connection> ... IP or dns-name; ssh <ip> possible too
exit ... ending a session

ssh -i <pub-key of user/ansible/...> <target ip> ... connection to remote with keys (next subsection)

The Advanced Section
-------------------

sshd -t ... test mode

/etc/ssh/ssh_config ... configuration path --> e.g. deactivate password authentificatio

Configure SSH-keys
-------------------

Client / local site:
ssh-keygen -t ed25519 -C <comment> ... generate keys
--> type ed25519 (more secure)
--> Press enter if it ask you where to save - if you have more, other as .ssh/<name of key> (dir ~/.ssh have to exist); for Windows: same xD
--> Passphrase: type whatever I want (Ansible: no passphrase)

--> Keys now stored under .ssh: .pub --> public key (Comment behind, type in the beginning)

ssh-copy-id -i <.pub file> <target-ip> ... Copy public key to remote site (and target user); for Windows: use scp or sftp (next subsection) instead of ssh-copy-id
--> i ... inputfile

now on remote site: --> ssh <IP> --> Asking for passphrase now :D
ls -la .ssh/<...>authorized_keys ... keys stored here (for Linux)

Tips
-------------------

Information: for <e.g. ansible>: add a new key (not the key from user)
--> Watch out, what's prompted: sometimes original and not <e.g. ansible>-passphrase
--> for <e.g. ansible> direct connection

eval $(ssh-agent) && ssh-add ... ask for passphrase and save it in ssh-agent
--> if you don't want to type in the passphrase every time: ssh-agent is running in the background
--> no more typing the passphrase ... but not really permanent

SCP
-------------------

transfering files via ssh

scp <source file> <destination file> ... ssh copy
--> for remote sites: <user>@<IP/DNS-Name>:<path> e.g. ben@172.18.211.140:/home/ben/.ssh
--> source or destination can be remote

SFTP
-------------------

transfering files via ssh

sftp <user>@<connection> ... establish SSH-connection; IP or dns-name; sftp <ip> possible too
-i ... identity file (like ssh)
-P ... specific port
--> now Interactiv commands

exit ... ending a session

cd, chmod, chgrp, chown, cp, df, ls, mkdir, rm, pwd ... like normal Linux (see further sections), but for remote site

get <remote path> <local path> ... Download, take remote path and copy to local path; when local not specified, same like remote
-p ... copy permissions and access times too
-R ... copy recursivly

put <local path> <remote path> ... Upload, same like get, but other direction: from local to remote
-p ... copy permissions and access times too
-R ... copy recursivly

lmdir <path> ... like mkdir; for local site (see further sections)

lcd ... like cd; for local site (see further sections)

lpwd ... like pwd; for local site (see further sections)

Special Linux Directories
------------------------------------------------------------------------------------------------------------------------------

/ ... root-dir

/root ... Home of root-user

/bin ... Binairies requiered by all
/sbin ... Binairies esential for system; important commands for system administration

/sys ... Virtual pseudo-filesystem giving information about the system and the hardware; can used to alter system parameters and for debugging
/srv ... Site-specific data served up by the system
/tmp ... Temporary files; on some distributions erased across a reboot and/or may actually be a ramdisk in memory
/usr ... Multi-user applications, utilities and data
/run ... for programms, when they have to temporarily store important information; regenerated after every reboot

1. -- Preparing (Example)

0 10 * * * /tmp/myjob.sh

┌───────────── Minute (0 - 59)

Systemd-Units
--------------------

to manage it like a normal process
see more here: https://devops.aibit.im/de/article/how-to-create-manage-systemd-timer-units

1. Create an executable file (sh) (don't forget to give the permissions: chmod +x <file>)

2. Create Service Unit (best practice: under /etc/systemd/system as .service)
e.g.:
[Unit]
Description=prints "Hello world all the time"

[Service]
Type=oneshot                                       #execute and the terminates
ExecStart=/etc/systemd/system/helloworld.sh        #link to file
User=abc                                           #optional: no run as root
Group=abc                                          #optional: like user

3. Create Timer Unit (best practice: under /etc/systemd/system as .timer)
e.g.:
[Unit]
Description=Hello World minütlich ausgeben

[Timer]
OnBootSec=1min                                     #executes 1min after start
OnUnitActiveSec=1min                               #after first run, run 1min later again -- repetation
Unit=helloworld.service                            #what should be run

[Install]
WantedBy=timers.target                             #its a timer unit

Other options for [Timer]
Persistent=true                                     #as soon as possible after booting
OnCalendar=daily                                    #when should timer start
    hourly: every hour
    weekly: every week (same as Mon *-*-* 00:00:00).
    Sun *-*-* 10:00: every sunday 10 o'clock.
    *-*-15 14:30: Am 15. every 15th day in month 14:30 o'clock.
    Mon..Fri *-*-* 09:00: Mon, Tue, Wen, Thu, Fri 9 o'clock.
OnUnitInactiveSec                                   #after ... min/sec of inactivation run --> repetation
AccuracySec                                         #systemd wake up process, so its not perfect 9:00:00 (+/- some seconds); standard: 1min 
RandomizedDelaySec=10sec                            #random delay till 10 sec

4. Enable the timer unit (sometimes not nescessary): systemctl enable <Timer-unit>

5. Start timer unit: systemctl start <Timer-unit>

Permissions
------------------------------------------------------------------------------------------------------------------------------

--> for sudo see section "more rights"

reprented with 9 characters:
r... read, w... write, x... execute, -... no permission
first 3: permissions for user
next 3: permissions for group
last 3: permissions for other (not user AND NOT group)

rwxrw-r-- --> all permissions for user, read and write for group, read for other (not user AND NOT group)

represented with numbers:
4... read, 2... write, 1... execute
first number for user
second for group
last for other

764 --> same as above

set permissions:
chmod +r <filename> ... '-' to take the permissions, '=' exact this permissions, w,x for other permissions
chmod o+rx ... give others the permission to read and execute
chmod 755 <filename> ... more granular

ls -l <file/dir>
ls -al | grep <filename> ... see permissions
ls -ld <dir/file> ... see permissions

chown <owner> <file> ... edit owner
-R ... for all files in this dir

chgrp ... editing group for file
chown <usr>:<group> <file> ... can leave usr empty

Information: Run a executable code inside a file needs rx, because it has to read the code
Information: To cd in a dir, need x

Sticky Bit: only owner can delete
represented with t on last digit, T when "other" has no x
representation with numbers: +1 before usual permissions, e.g. "1755"

Setuid Bit: operates in dir with uid of owner
represented with s on 3rd digit, S when "user" has no x
representation with numbers: +4 before usual permissions, e.g. "4755"
--> e.g. script executable only as root, but normal users should use

Setgid Bit: operates in dir with gid of owner
represented with s on 6th digit, S when "group" has no x
representation with numbers: +2 before usual permissions, e.g. "2755"
--> new files get gid as owner

Finding Permission

find -perm -755 -type f -exec chmod 600 {} \; ... every founded file --> change permission to 600

Routing information: rules priority in this order Source, Interface, Default Zone/Interface

Rich Language
----------------------

more complex firewall settings, extends the current zone elements

--> if some interact/contradict, first rule matches wins (like normal firewall)

option (only one):

--> end, e.g. 1GiB (not the size!), 66% --> till 66% of disk

parted rm <device> <partition number> ... remove Partition >partition number>

Logical Volume Group (LVM)
------------------------------------------------------------------------------------------------------------------------------

--> "virtualisation of storage"
--> extends chapter "Managing Storage"

Show Informations
----------------------

Physical Volume (PV) ... physical storage, partition
Volume Group (VG) ... groups every physical volume
Logical Volume (LG) ... a file system within the volume group

pvs ... information about PV's
vgs ... information about VG's
lvs ... information about LV's

same, but more information:
pvdisplay
vgdisplay
lvdisplay

Creation
----------------------

pvcreate <device> ... initializes PV on a device, to belong to LVM; will overwrite partition!
Reminder: Devices (lsblk) under /dev

vgcreate <name> <device> ... generate new VG and adds PV; will pvcreate on device automatically, when pvcreate was not made before; VG cannot be empty
Reminder: Devices (lsblk) under /dev
Technical: writes meta data on device, so device know to which VG

lvcreate -n <name> -L <size> <VG> ... creates logical volume; minimum
-L <size> ... defines size, e.g. 500M
--> man-Page really good, raid and thin provisioning possible
--> create file system and mount it!
--> accessible under /<mnt dir>/<VG>/<LV> --> link made by mapper

/dev/mapper ... shows links from mapper

Extending Storage
----------------------

lvextend -L +<size> <LV> ... extend LV, size e.g. +300M
--> LV path or LV name (Attention: LV name not unique! (only in VG), VG/LV or mapper-path possible too)
lvextend -L <size> <LV> ... resize exactly on size
lvextend -l +<size>%FREE <LV> ... small l!, use <size> available space for it, e.g. +100%FREE --> use 100% of remaining space of VG
-r ... resize file system automatically --> otherwise LV extended, but file system remains on same size!

resizing file system:
xfs_growfs <mountpoint of file system> ... for xfs, extend file system on hole device
resize2fs <device> ... for ext4, extend file system on hole device

vgextend <name> <device> ... extends VG with <device>, when VG exists; will pvcreate on device automatically, when pvcreate was not made before

Shrink Storage
----------------------

xfs cannot shrink!
only ext4, but have to be unmounted; fs first, then LV (can delete data permanently!)
lvextend -L -<size> <LV> ... extend LV, size e.g. -300M; LV name or LV path

Removing a device
----------------------

pvmove <device> ... move data from <device> to another PV
--> then remove

Removing / Deleting
----------------------

unmount LV first! Don't forget /etc/fstab

lvremove <LV> ... remove LV
--> LV path or LV name (Attention: LV name not unique! (only in VG), VG/LV or mapper-path possible too)

vgremove <VG> ... remove VG

pvremove <device> ... remove LVM-disk-label from device

Contexts
----------------------

every service is only allowed to access, when context is correct - even if the permissions are correct!

ls -Z <file> ... see context of a file/dir
--> type always marked with _t
ps -eZ <process> ... context of processes
id -Z <user> ... context of user

semanage fcontext -at <context-type> <file/dir> ... edit/add context to a specific file/dir
--> most common case: 403 Http
  - control over setenforce or jornalctl, if error by SELinux
  - list contexts with semanage (to see whats wrong, correct http-path e.g. is /var/www/html)
  - correct contexts
--> examples man-page
--> for recursive changes use <dir>(/.*) (then don't forget "<dir>")
--> new files would inherit the context because of the policy
--> have to use restorecon for correct relabeling

restorecon <file/dir> ... restore/correct contexts; used, when context edited with semanage and the context has to be changed for the underlaying files and directories
-r ... recursive
-v ... verbose, show informations

chcon -t <context-type> <file/dir> ... same like semanage, but without creating a rule in policy (restorecon would remove this change, because there is no policy rule); new files in a dir would not inherit the context

Ports
----------------------

Environment Variables
----------------------

Information: EVERY var in plaintext

secret create <var> <value> ... give container a secret; value can be a file, where many vars are stored (each line one)
--env=true ... use secret as environment variable

Quadlets / Automation with Systemd
----------------------

--> man podman-systemd.unit
--> man podman-container.unit
not as complicated as it seems to be
--> not the same in docker!

create a file (recommended: <name>.container) and save under ~/.config/containers/systemd/

file:
>>
[Unit]
Description=Write something useful

[Container]
Image=<image>
ContainerName=<name>
PublishPort=<published port>:<container-port>
Volume=<Host-Dir>:<container-dir>:<options>
Environment=<var>=<value>
EnvironmentFile=<file>
Exec=<cmd> 

[Install]
WantedBy=default.target
<<

--> like podman run, every option has a line (see man podman-systemd.unit --> table)

--> management by systemd
--> systemctl enable doesn't work --> systemctl --user daemon-reload (after every change, the deamon look up and refreshs, starting the container)

systemctl --user <start/stop/...> <container>.service ... managing over systemd
--> --user nescessary

Problem: Podman start only when user is logged in
loginctl enable-linger <user> ... process manager starts with boot and ends when system shutdown --> container will be startet with boot
loginctl disable-linger <user>
